# Application Latency Diagnostic Scripts

## Scripts

| Script | Purpose |
| --- | --- |
| `Invoke-LatencyDiagnostic.ps1` | Collects application, platform, model, database, configuration, revision, replica, and metric evidence into a timestamped directory and ZIP archive. |
| `Invoke-ContainerNetworkChecks.ps1` | Runs unauthenticated DNS and HTTP phase-timing checks from inside the proxy container. |
| `New-SyntheticRequest.ps1` | Creates a customer-data-free streaming request template for a controlled test. |
| `Find-CorrelationId.ps1` | Searches Container Apps and workspace-based Application Insights telemetry for candidate application correlation IDs in a known UTC window. |
| `Get-LatencyObservedPattern.ps1` | Classifies the collected evidence and reports the most likely observed latency pattern, confidence, supporting signals, and next action. The main collector runs it automatically. |

## Prerequisites

- PowerShell 7 or later.
- Azure CLI installed and authenticated.
- The Azure CLI Container Apps extension.
- `curl.exe` when running a new client test.
- Azure permissions to read:
  - The subscription and resource group.
  - Both Container Apps and their revisions, replicas, and logs.
  - The Azure OpenAI account and Azure Monitor metrics.
  - PostgreSQL Flexible Server and Azure Monitor metrics.
  - The Log Analytics workspace.
  - Private endpoints and private DNS zones, if those exports are required.
- Permission to execute a shell in the proxy Container App for the network-check script.

Install or update the Container Apps extension:

```powershell
az extension add --name containerapp --upgrade --allow-preview false
az login
az account show --output table
```

All examples assume the Container Apps, Azure OpenAI account, and PostgreSQL server are in the resource group supplied through `-ResourceGroup`.

## Diagnostic settings expected

The main collector looks for the following telemetry when available:

| Resource | Expected telemetry |
| --- | --- |
| Container Apps | Console logs, system logs, HTTP ingress logs, requests, response time, replicas, restarts, CPU, memory, and network metrics |
| Application Insights/OpenTelemetry | `requests`, `dependencies`, `traces`, `exceptions`, and `customEvents` |
| Azure OpenAI | Request/response diagnostics, request usage, audit or trace data, time to response, token timing, total latency, requests, token counts, and active-token metrics |
| PostgreSQL | Server logs, Query Store runtime, Query Store waits, session activity, CPU, memory, connections, IOPS, disk queue, and network metrics |

Table and metric availability varies by resource configuration, deployment type, region, and diagnostic setting mode. Optional queries that cannot run are saved with their error output and reported as warnings.

## Finding a correlation ID

`Invoke-LatencyDiagnostic.ps1 -RunId` expects the identifier that the application
records across the proxy, OpenWebUI, Application Insights, and ideally the Azure
OpenAI request. Use an explicit application value such as `x-client-request-id`,
`x-correlation-id`, or the proxy's structured `request_id`.

Do not automatically substitute an Azure OpenAI `CorrelationId`,
`apim-request-id`, or an Application Insights `operation_Id`. Those identifiers
are generated at different layers and only correlate the full path when the
application records or propagates them.

### For a test generated by these scripts

The main collector creates and prints the ID before sending the request. You can
also recover it from:

- The evidence directory name: `latency-evidence\<RUN_ID>`.
- `context.json` in the `runId` property.
- `client-timing.txt` in the `run_id` value.
- `client-response-headers.txt` if the proxy echoes the selected correlation
  header.

The generated ID is sent as `x-client-request-id` unless
`-CorrelationHeader` specifies another header.

### For an existing user request

Use the narrowest known UTC window and check these sources in order:

1. Proxy structured logs for `request_id`, `x-client-request-id`, or
   `x-correlation-id`.
2. Browser or API-client network details for the correlation request or response
   header. Record the request time in UTC as well.
3. Application Insights transaction search and trace details. Prefer an explicit
   correlation value in custom dimensions; use `operation_Id` only when the
   application propagates it.
4. Azure OpenAI resource logs for service-side investigation after the
   application request has been identified. The service `CorrelationId` is not
   necessarily the application's ID.

`Find-CorrelationId.ps1` searches the first three telemetry sources and labels
Application Insights operation IDs as fallbacks:

```powershell
.\Find-CorrelationId.ps1 `
  -SubscriptionId "<SUBSCRIPTION_ID>" `
  -WorkspaceId "<LOG_ANALYTICS_WORKSPACE_CUSTOMER_ID>" `
  -ProxyApp "<PROXY_CONTAINER_APP>" `
  -StartUtc "2026-08-20T17:00:00Z" `
  -EndUtc "2026-08-20T17:15:00Z"
```

When several requests occurred in the window, narrow the results with a known
path, message fragment, model name, or other non-sensitive log text:

```powershell
.\Find-CorrelationId.ps1 `
  -SubscriptionId "<SUBSCRIPTION_ID>" `
  -WorkspaceId "<LOG_ANALYTICS_WORKSPACE_CUSTOMER_ID>" `
  -ProxyApp "<PROXY_CONTAINER_APP>" `
  -SearchText "/v1/responses" `
  -Hours 2 `
  -OnlyExplicitCorrelationIds
```

Use the selected ID and the same padded UTC window with the collector:

```powershell
.\Invoke-LatencyDiagnostic.ps1 `
  <resource parameters> `
  -RunId "<CORRELATION_ID>" `
  -StartUtc "<PADDED_START_UTC>" `
  -EndUtc "<PADDED_END_UTC>" `
  -SkipClientTest
```

If the lookup returns no explicit ID, the proxy likely does not log the incoming
correlation header. Use a descriptive unique `-RunId` to collect window-level
evidence, but understand that correlation-specific queries will be empty. For
future requests, emit the same `request_id` on every structured proxy event,
forward it to downstream calls, and return it as a response header.

## Workflow A: Analyze already collected logs

Use this workflow for an existing incident. Provide:

- The existing application correlation ID, if one is available.
- A UTC window that covers the incident, with several minutes of padding.
- `-SkipClientTest` so no new request is sent.

```powershell
.\Invoke-LatencyDiagnostic.ps1 `
  -SubscriptionId "<SUBSCRIPTION_ID>" `
  -ResourceGroup "<RESOURCE_GROUP>" `
  -ProxyApp "<PROXY_CONTAINER_APP>" `
  -OpenWebUiApp "<OPENWEBUI_CONTAINER_APP>" `
  -AoaiAccount "<AZURE_OPENAI_ACCOUNT>" `
  -AoaiDeployment "<DEPLOYMENT_NAME>" `
  -PostgresServer "<POSTGRES_SERVER>" `
  -WorkspaceId "<LOG_ANALYTICS_WORKSPACE_CUSTOMER_ID>" `
  -RunId "<EXISTING_CORRELATION_ID>" `
  -StartUtc "2026-08-20T17:00:00Z" `
  -EndUtc "2026-08-20T17:15:00Z" `
  -SkipClientTest
```

If no correlation ID exists, provide a descriptive unique value for `-RunId`. Resource-level logs and metrics will still be collected for the time window, but correlation-specific application queries may return no rows.

## Workflow B: Generate and collect a new test

### 1. Create a synthetic request

```powershell
.\New-SyntheticRequest.ps1 `
  -Model "<MODEL_OR_DEPLOYMENT_NAME>" `
  -OutputPath ".\synthetic-request.json"
```

Review the resulting JSON before use. Adjust its property names and API shape to match the proxy's actual request contract. Keep streaming enabled and background processing disabled.

### 2. Run the diagnostic

```powershell
.\Invoke-LatencyDiagnostic.ps1 `
  -SubscriptionId "<SUBSCRIPTION_ID>" `
  -ResourceGroup "<RESOURCE_GROUP>" `
  -ProxyApp "<PROXY_CONTAINER_APP>" `
  -OpenWebUiApp "<OPENWEBUI_CONTAINER_APP>" `
  -AoaiAccount "<AZURE_OPENAI_ACCOUNT>" `
  -AoaiDeployment "<DEPLOYMENT_NAME>" `
  -PostgresServer "<POSTGRES_SERVER>" `
  -WorkspaceId "<LOG_ANALYTICS_WORKSPACE_CUSTOMER_ID>" `
  -CodexUrl "https://<CODEX_API_HOST>/<API_PATH>" `
  -RequestBodyPath ".\synthetic-request.json"
```

The script prompts for a short-lived bearer token as a secure string. It sends the token to `curl.exe` through standard input instead of including it in the process command line.

The generated correlation ID has this format:

```text
latency-YYYYMMDDTHHMMSSZ-xxxxxxxx
```

The script places the correlation ID in the `x-client-request-id` header by default. If the application uses a different header:

```powershell
-CorrelationHeader "x-correlation-id"
```

For a newly generated test, wait for telemetry ingestion if the first collection does not contain the request. Then rerun the script with the generated run ID, the original UTC window, and `-SkipClientTest`.

## Workflow C: Run in-container network checks

This script resolves the Azure OpenAI, PostgreSQL, and OpenWebUI hostnames from inside the proxy container. It measures DNS, TCP connect, TLS, first-byte, and total time for unauthenticated HTTPS probes.

```powershell
.\Invoke-ContainerNetworkChecks.ps1 `
  -SubscriptionId "<SUBSCRIPTION_ID>" `
  -ResourceGroup "<RESOURCE_GROUP>" `
  -ProxyApp "<PROXY_CONTAINER_APP>" `
  -AoaiHost "<ACCOUNT_NAME>.openai.azure.com" `
  -PostgresHost "<SERVER_NAME>.postgres.database.azure.com" `
  -OpenWebUiHost "<OPENWEBUI_HOST>" `
  -OutputPath ".\container-network-checks.txt"
```

An HTTP `401` or `403` is expected from an unauthenticated probe. The relevant values are:

- Resolved IP address.
- DNS lookup time.
- TCP connect time.
- TLS negotiation time.
- Time to first byte.
- Total request time.

The container image must include `/bin/sh`, `curl`, and either `getent` or `nslookup`.

## Output

By default, the main script creates:

```text
.\latency-evidence\<RUN_ID>\
.\latency-evidence\<RUN_ID>.zip
```

Use `-OutputRoot` to place evidence elsewhere:

```powershell
-OutputRoot "C:\Diagnostics\latency-evidence"
```

Typical output includes:

- `context.json`: Run ID, UTC window, resource names, resource IDs, and test mode.
- `client-timing.txt`: HTTP status and DNS, connect, TLS, first-byte, and total timing.
- `client-response-headers.txt`: Response headers from a generated test.
- `client-response.ndjson`: Raw streamed response from a generated test.
- `request.json`: Synthetic request used by a generated test.
- `proxy-config.json` and `openwebui-config.json`: Ingress, scale, resources, and probes.
- Revision and replica inventories for both Container Apps.
- Recent console and system log tails.
- KQL files and their JSON results.
- Azure OpenAI, Container Apps, and PostgreSQL metric definitions and supported metrics.
- Private endpoint and private DNS inventories.
- `observed-pattern-summary.txt`: Human-readable primary pattern, confidence, supporting evidence, and recommended next action.
- `observed-pattern-summary.json`: Machine-readable classification, ranked additional patterns, measured signals, and thresholds.
- `manifest.csv`: File inventory for the evidence package.

## Interpreting the results

| Observed pattern | Most likely area |
| --- | --- |
| Azure OpenAI time to response is low, but client first byte is high | Authentication, proxy processing, ingress, buffering, networking, or client behavior |
| Authentication duration and `/api/v1/models` are slow | OpenWebUI, public routing, token validation, or PostgreSQL |
| First request after idle is slow, but warm requests are normal | Container Apps startup, readiness, or scale-to-zero |
| Upstream first chunk is timely, but proxy first flush is delayed | Proxy middleware, compression, ingress, or response buffering |
| Azure OpenAI latency rises with prompt tokens | Prompt processing, cache behavior, model behavior, or context size |
| `429` responses or retries occur before success | Deployment capacity, quota, concurrency, or retry policy |
| PostgreSQL and OpenWebUI dependency latency rise together | Database, connection pool, IOPS, waits, or slow queries |
| DNS, connect, or TLS phases are high | DNS forwarding, routing, firewall/NVA inspection, public hairpin, or TLS |

Use multiple identical runs before changing architecture or capacity. A single sample is not enough to establish causality.

### Automatic observed-pattern analysis

At the end of collection, the main script automatically runs `Get-LatencyObservedPattern.ps1` and prints a result such as:

```text
Observed pattern: Application or proxy overhead after a timely model response
Confidence: Medium
```

The analyzer evaluates available evidence for:

- Azure OpenAI throttling, retries, or service failures.
- Slow DNS, TCP connection, or TLS phases.
- Authentication or OpenWebUI validation latency.
- Proxy or ingress response buffering.
- Application overhead when Azure OpenAI responds promptly.
- Azure OpenAI first-response latency.
- Slow generation after the first token.
- Container Apps lifecycle, scaling, restart, or probe activity.
- PostgreSQL pressure or waits.

The classification is deliberately conservative. It reports `No conclusive latency pattern detected` when the required signals are missing or do not cross the configured thresholds. It identifies an evidence-supported pattern, not a proven root cause.

The analyzer can also be rerun after telemetry ingestion:

```powershell
.\Get-LatencyObservedPattern.ps1 `
  -EvidencePath ".\latency-evidence\<RUN_ID>"
```

Thresholds can be adjusted when the application's service-level objectives differ:

```powershell
.\Get-LatencyObservedPattern.ps1 `
  -EvidencePath ".\latency-evidence\<RUN_ID>" `
  -SlowClientFirstByteSeconds 3 `
  -SlowModelFirstResponseMilliseconds 3000 `
  -SlowAuthenticationMilliseconds 1000 `
  -SlowFlushMilliseconds 250
```

## Security and data handling

- Use only synthetic prompts.
- Use a short-lived test token.
- Do not place tokens in command history, scripts, configuration files, or tickets.
- Do not share raw request bodies, model responses, or headers without review.
- Inspect and redact the evidence directory before sharing its ZIP archive.
- Treat application traces and database logs as potentially sensitive.
- Store evidence only in an approved location and follow the applicable retention policy.

## Troubleshooting

### A query produces an error file or warning

Confirm that the corresponding diagnostic category is enabled and routed to the supplied workspace. Table names differ between Azure Diagnostics mode and resource-specific mode. The generated `.kql` file shows the exact query that was attempted.

### Application Insights queries return no rows

Confirm that Application Insights telemetry is routed to the supplied workspace and that the application records the selected correlation header in `operation_Id`, `customDimensions`, or message content.

### The generated request is missing from Log Analytics

Wait for telemetry ingestion, then rerun the main script with:

- The same `-RunId`.
- The original `-StartUtc` and `-EndUtc`.
- `-SkipClientTest`.

### A metric is listed as unavailable

The script first retrieves metric definitions and requests only metrics supported by the resource. Review the generated `*-metric-definitions.json` and `*-unavailable-metrics.txt` files.

### Container execution fails

Confirm that the operator can execute commands in the Container App and that a running replica exists. The image must contain the shell and network tools used by the script.

### Resources are in different resource groups

The current main script accepts one resource group for all four resources. Run separate targeted Azure CLI queries or adapt the resource-group parameters before use in an architecture where resources are split across groups.
